# Регламент полевых испытаний драйверов на площадке (Field Pilot)

> **Статус:** Lab — методика проведения полевых испытаний промышленных протоколов (Modbus TCP, MQTT, OPC UA) на объекте заказчика. Метки зрелости: [doc-status.md](doc-status.md).

Этот документ описывает порядок приёмочных испытаний промышленных драйверов ISPF непосредственно в технологической сети предприятия: проверку чтения и обратной записи уставок, наполнения архива истории, отображения на мнемосхемах и непрерывного 7-дневного прогона под нагрузкой.

**Связанные разделы:** [Уровни зрелости драйверов](driver-promotion.md) · [Лаборатория совместимости драйверов](driver-interop-lab.md) · [Чеклист полевых доказательств C1](../en/field-c1-evidence-checklist.md) · [Справочник драйверов](drivers.md).

## 1. Правило допуска драйвера к промышленной эксплуатации

Метка **`PRODUCTION`** в коде драйвера означает, что он успешно прошёл автоматические стендовые испытания на программных эмуляторах в лаборатории (`DriverProductionMatrixTest`).

Чтобы конкретный сценарий и модель ПЛК получили статус **прошедших полевую приёмку (`ready-for-field`)**, выполняются четыре шага:
1. Оформляется паспорт площадки и перечень проверяемого оборудования (см. [Чеклист C1](../en/field-c1-evidence-checklist.md)).
2. Проводится предварительный прогон на лабораторном стенде (`deploy/driver-interop/`).
3. Выполняется подключение на площадке и **непрерывный 7-дневный прогон** с заполнением журнала наблюдений.
4. Оформляется акт приёмки с подписью инженера АСУ ТП площадки.

## 2. Три типовых сценария полевых испытаний

| Сценарий | Основные драйверы | Типовой объект | Критерии успешного прохождения |
|----------|-------------------|----------------|--------------------------------|
| **1. Участок ПЛК Modbus TCP** | `modbus-tcp` | Насосная станция, резервуарный парк, котельная | Опрос 50+ регистров с периодом до 2 с, обратная запись уставок (`FC6` / `FC16`), живая мнемосхема |
| **2. Парк промышленных шлюзов MQTT** | `mqtt` | Распределённые узлы учёта и телеметрии через общий брокер | 10+ шлюзов на брокере, пакетный приём до 1 000 сообщений/мин без потерь, тревога при потере связи |
| **3. Производственная линия OPC UA** | `opcua`, `opcua-server` | Сборочная или упаковочная линия с контроллерами OPC UA | Подписка на теги с задержкой до 500 мс, запись уставок, отдача агрегированных тегов внешним системам через `opcua-server` |

## 3. Сценарий 1 — Участок ПЛК Modbus TCP

### Настройка подключения устройства

| Параметр | Пример значения |
|----------|-----------------|
| `driverId` | `modbus-tcp` |
| `host` | `198.51.100.50` |
| `port` | `502` |
| `pollIntervalMs` | `1000` |
| `unitId` | `1` |

Сопоставьте регистры контроллера переменным узла `DEVICE` (например, регистр хранения `40001` → переменная `level`). Подробный формат адресов приведён в разделе **[Драйверы устройств (`modbus-tcp`)](drivers.md)**.

### Контрольный список на площадке
1. **Связь:** устройство переходит в статус `RUNNING`, в журнале сервера отсутствуют ошибки `DriverException`.
2. **Чтение:** все 50+ привязанных переменных обновляются за 1–2 цикла опроса с признаком качества `GOOD`.
3. **Запись уставки:** изменение записываемой переменной оператором (`PUT /api/v1/objects/by-path/variables`) корректно меняет значение регистра в ПЛК.
4. **Архив истории:** `GET /api/v1/objects/by-path/variables/history` возвращает сохранённые точки по ключевым параметрам.
5. **Экран оператора:** мнемосхема отображает живые показания, а при отсоединении кабеля ПЛК выводит индикатор потери связи.

Предварительная проверка в лаборатории:

```bash
docker compose -f deploy/driver-interop/docker-compose.yml up -d --wait
bash deploy/tools/driver-interop-smoke.sh
./gradlew :packages:ispf-driver-modbus:test
```

## 4. Сценарий 2 — Парк шлюзов MQTT

### Настройка подключения

| Параметр | Пример значения |
|----------|-----------------|
| `driverId` | `mqtt` |
| `brokerUrl` | `tcp://mqtt.plant.local:1883` |
| `clientId` | `ispf-fleet-01` |
| `topicPrefix` | `plant/line1/{deviceId}/telemetry` |

### Контрольный список на площадке
1. **Приём потока:** все 10+ шлюзов отображаются онлайн, переменные обновляются по мере прихода JSON-сообщений.
2. **Пиковая нагрузка:** при подаче ~1 000 сообщений в минуту в течение 10 минут очередь приёма не переполняется.
3. **Обратная команда:** публикация команды управления в топик устройства доходит до шлюза в пределах заданного норматива времени.
4. **Контроль устаревания:** при отключении шлюза на время более `3 × pollIntervalMs` срабатывает правило тревоги потери связи.
5. **Выгрузка архива:** история ключевого тега корректно выгружается в CSV.

## 5. Сценарий 3 — Производственная линия OPC UA

### Настройка клиента (`opcua`) и встроенного сервера (`opcua-server`)

| Параметр клиента `opcua` | Пример | Параметр сервера `opcua-server` | Пример |
|--------------------------|--------|---------------------------------|--------|
| `driverId` | `opcua` | `driverId` | `opcua-server` |
| `endpointUrl` | `opc.tcp://198.51.100.20:4840` | `bindPort` | `4840` |
| `readMode` | `subscribe` | `namespace` | `2` |
| `timeoutMs` | `10000` | `securityPolicy` | `Basic256Sha256` (с каталогом сертификатов `pkiDir`) |

### Контрольный список на площадке
1. **Обзор адресного пространства:** дерево узлов контроллера и папка `Objects/IspfVariables` читаются внешним клиентом (например, UAExpert).
2. **Подписка:** изменения тегов приходят по подписке с задержкой менее 500 мс.
3. **Двусторонняя запись:** запись уставки из интерфейса ISPF меняет тег в контроллере, а запись из внешнего клиента OPC UA в `opcua-server` обновляет переменную в дереве ISPF.

## 6. Журнал 7-дневного непрерывного прогона

Заполняется ежедневно в течение 7 суток контрольной эксплуатации:

| День | Дата | Активных тегов | Критические сбои (P0 / P1) | Архив истории в норме | Экраны оператора в норме | Примечания |
|------|------|----------------|----------------------------|:---------------------:|:------------------------:|------------|
| 1 | | | | ☐ | ☐ | |
| 2 | | | | ☐ | ☐ | |
| 3 | | | | ☐ | ☐ | |
| 4 | | | | ☐ | ☐ | |
| 5 | | | | ☐ | ☐ | |
| 6 | | | | ☐ | ☐ | |
| 7 | | | | ☐ | ☐ | Готов к подписанию акта |

К критическим сбоям (`P0`) относятся: зависание или падение драйвера, потеря точек архива более чем на 1 час, ошибочная адресация при записи уставки.

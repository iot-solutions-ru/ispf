# Приёмка исполнения плана MES

Лабораторный контур внутри `mes-platform`. Расчёт плана остаётся снаружи. Живые цеховые источники в этот пакет не входят.

| Проверка | Что делает пакет |
|---|---|
| AM-01 | Новый кандидат не переписывает уже записанный снимок официального плана |
| AM-02 | Устаревший актив не выглядит как нулевой выпуск (`mes_plan_getDataReadiness` = `partial` на линии `LINE-A01`) |
| AM-03 | Статус качества `blocked` запрещает проверку и публикацию |
| AM-04 | Заблокированный ресурс охлаждения нельзя зарезервировать |
| AM-05 | `mes_plan_publish` создаёт один официальный id `PUB-<кандидат>` и снимок `SNAP-<кандидат>` |
| AM-06 | Комментарий планера не публикует заблокированную номенклатуру |
| AM-07 | Публикация возможна только после статуса проверки `ready` |
| AM-08 | Повтор публикации возвращает тот же официальный id |
| AM-09 | `mes_plan_rejectPub` требует причину |
| AM-10 | Перепубликация помечает старый план `replaced` и оставляет факт на старом id |
| AM-11 | Задержка больше 30 минут открывает отклонение Warning |
| AM-12 | Закрытие периода создаёт один хвост; повтор возвращает тот же id |
| AM-13 | План против факта читает выбранный официальный id |
| AM-14 | Статус доставки получателю отделён от официального плана (`mes_plan_setDelivery`) |
| AM-15 | Блокировка качества — результат функции, её не обходят ролью |
| AM-16 | Снимки только добавляются в `mes_exec_snapshot` |

Лабораторная карта AM-01…16. `MesPlanExecutionIntegrationTest` покрывает happy-path плюс reject без причины, SKU-гейт на publish, замороженный снимок, доставки при republish и проверки статуса accept/reject (деплой с `?withSeeds=true`). Пустая площадка даёт readiness `empty`, не `ready`. Production-зеркало в этом тесте не проверяется.

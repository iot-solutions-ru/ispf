# Нагрузочное тестирование конвейера телеметрии и событий

> **Статус:** Lab — методика и скрипты нагрузочных испытаний конвейера приёма телеметрии, журнала событий и архива истории переменных. Метки зрелости: [doc-status.md](doc-status.md).

Этот документ описывает набор нагрузочных сценариев для замера пропускной способности основных путей обработки данных в ISPF:
- приём телеметрии по MQTT и прямая запись в архив истории (`TELEMETRY_ONLY`);
- маршрутизация телеметрии через шлюз `mqtt-gateway` на дочерние датчики;
- прямая пакетная запись в журнал событий (`EVENT_JOURNAL_ONLY`, [ADR-0027](decisions/0027-event-journal-ingress-fast-path.md));
- полный проход через конвейер автоматизации с вычислением формул CEL (`FULL`);
- публикация событий через HTTP REST API (`POST /api/v1/events/fire`).

> **Важно:** абсолютные цифры (сообщений и точек в секунду) напрямую зависят от числа ядер процессора, типа дисков и выбранного хранилища (PostgreSQL/TimescaleDB, ClickHouse или ScyllaDB). Используйте приведённые ниже сценарии для сравнения конфигураций и контроля отсутствия регрессий на вашем стенде. Перед запуском нагрузочных тестов включайте профиль **`throughput`** ([Профили развёртывания](demostands.md)).

**Связанные разделы:** [Профили развёртывания (`demostands.md`)](demostands.md) · [Мониторинг и диагностика (`observability.md`)](observability.md) · [Стресс-тест истории MQTT (`lab-mqtt-historian-stress.md`)](lab-mqtt-historian-stress.md) · [Стресс-тест журнала событий (`lab-event-journal-stress.md`)](lab-event-journal-stress.md).

## 1. Набор эталонных нагрузочных сценариев (`I-01` … `I-08`)

Сводные отчёты лабораторных прогонов хранятся в [`examples/lab-mqtt-historian-stress/reports/ordered-suite-i01-i08.md`](../../examples/lab-mqtt-historian-stress/reports/ordered-suite-i01-i08.md):

| Код сценария | Проверяемый маршрут | Описание и ориентир на выделенном стенде |
|--------------|---------------------|------------------------------------------|
| **`I-01`** | `N` драйверов `mqtt` (`TELEMETRY_ONLY`) → архив истории | Прямая пакетная запись точек истории в ClickHouse / ScyllaDB (на 16 потоках драйверов со слиянием пакетов или без него) — подробнее в [lab-mqtt-historian-stress.md](lab-mqtt-historian-stress.md) |
| **`I-02`** | Шлюз `mqtt-gateway` → дочерние датчики → архив истории | Приём мультиплексированного потока одним шлюзом, распределение по дочерним объектам (`dispatchTelemetry`) и запись истории — подробнее в [lab-mqtt-gateway-ingress.md](lab-mqtt-gateway-ingress.md) |
| **`I-03`** | Драйверы `mqtt` (`EVENT_JOURNAL_ONLY`) → журнал событий | Быстрый путь записи сырых событий в `event_history` в обход правил CEL — подробнее в [lab-mqtt-event-journal-ingress.md](lab-mqtt-event-journal-ingress.md) |
| **`I-04`** | Драйверы `mqtt` (`FULL`) + правила CEL → журнал событий | Полный цикл: обновление переменной, проверка условия тревоги на языке CEL и запись срабатывания в журнал |
| **`I-05`** | Драйвер `virtual` (`TELEMETRY_ONLY`) → архив истории | Периодический опрос 30 виртуальных устройств с записью временных рядов |
| **`I-06`** | Драйвер `virtual` (`FULL`) + правила CEL → журнал событий | Проверка скорости вычисления правил тревог при внутреннем периодическом опросе |
| **`I-07`** | Внешние клиенты HTTP → `POST /api/v1/events/fire` | Пропускная способность синхронного REST API приёма событий в несколько десятков параллельных потоков |
| **`I-08`** | Шлюз `mqtt-gateway` (`lastIngress.raw`) → архив истории | Запись неразобранных входящих пакетов шлюза напрямую в историю |

Запуск полного набора сценариев одной командой:

```bash
python deploy/run_lab_ordered_suite.py --topology single --profile grouped --continue-on-fail
python deploy/run_lab_ordered_suite.py --topology single --only I-07,I-08 --reset soft
```

## 2. Основные скрипты нагрузочного тестирования в каталоге `deploy/`

| Скрипт | Что измеряет |
|--------|--------------|
| `deploy/events-load-test.py` | Нагрузка на HTTP API: `POST /api/v1/events/fire` и `GET /api/v1/events` |
| `deploy/events-internal-load-test.py` | Внутренний конвейер: виртуальный драйвер → переменная `sineWave` → правило тревоги → журнал событий |
| `deploy/mqtt-ingress-load-test.py` | Поток сообщений из брокера MQTT → драйвер `mqtt` → архив истории или правила тревог |
| `deploy/mqtt-event-journal-test-remote.sh` | Быстрый путь записи MQTT-сообщений напрямую в журнал событий (`EVENT_JOURNAL_ONLY`) |
| `deploy/cluster-scale-load-test.py` | Проверка масштабирования пропускной способности при увеличении числа реплик кластера |

### Очистка стенда перед запуском замеров (`loadtest-cleanup.py`)

Чтобы фоновые демонстрационные устройства и старые тестовые корреляторы не искажали результаты замера, перед прогоном выполните скрипт очистки:

```powershell
python deploy/loadtest-cleanup.py
python deploy/loadtest-cleanup.py --purge-mqtt --purge-virtual
```

## 3. Как контролировать доставку без потерь во время теста

При больших объёмах данных (миллионы строк в ClickHouse или ScyllaDB) оценивайте скорость и полноту записи по монотонным счётчикам в `GET /api/v1/platform/metrics` (или `/actuator/prometheus`):
- **`variableHistoryFlushedTotal`** и **`variableHistoryQueueSize`** — сколько точек истории фактически сброшено на диск и сколько ожидает в памяти;
- **`eventsFiredTotal`**, **`eventJournalFlushedTotal`** и **`eventJournalQueueSize`** — сколько событий принято и сколько записано в таблицу журнала;
- **`telemetryCoalesceDropsTotal`** — сколько промежуточных значений было объединено при включённом окне слияния (`telemetryCoalesceMs`).

При корректно подобранном размере очереди после окончания генерации нагрузки размер очереди (`QueueSize`) плавно снижается до `0`, а число записанных точек совпадает с числом принятых сообщений.

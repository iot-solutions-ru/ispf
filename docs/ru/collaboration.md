# Совместная работа инженеров над деревом объектов

> **Статус:** Stable — защита от случайной перезаписи чужих правок (`revision`), журнал изменений, временная блокировка веток дерева (`lease`), пообъектные права и пакеты изменений (`change-sets`). Метки зрелости: [doc-status.md](doc-status.md).

Когда несколько инженеров одновременно настраивают одно дерево объектов ISPF, платформа предотвращает потерю правок с помощью контроля версий узлов, индикации присутствия, аренды поддеревьев и пакетов отложенного применения изменений.

---

## 1. Защита от конфликтов при одновременном редактировании (`revision`)

У каждого узла в таблице `object_nodes` есть целочисленный счётчик редакции **`revision`**, который автоматически увеличивается на `1` при каждом изменении метаданных, структуры переменных, функций или событий.

| Заголовок HTTP-запроса | Назначение |
|------------------------|------------|
| `If-Match: <ожидаемая_редакция>` | Передаётся при сохранении объекта (`PATCH` / `PUT`); если узел уже успел изменить другой инженер, сервер отклонит перезапись |
| `X-ISPF-Force: true` | Принудительное сохранение поверх чужих правок без проверки версии (доступно только роли `admin`) |

Если переданная в `If-Match` версия устарела, сервер возвращает код **`409 Conflict`** с указанием того, кто и когда сохранил более свежую версию:

```json
{
  "error": "REVISION_CONFLICT",
  "objectPath": "root.platform.devices.pump-01",
  "expectedRevision": 3,
  "currentRevision": 5,
  "changedBy": "ivan",
  "changedAt": "2026-06-21T12:00:00Z"
}
```

> Приход живой телеметрии с драйвера (`setDriverTelemetryValue`) и автоматический пересчёт правил (`propagateBindings`) **не увеличивают** счётчик `revision` и не мешают инженерам редактировать конфигурацию узла.

В веб-консоли при получении по WebSocket уведомления о том, что открытый вами объект только что изменил другой пользователь, появляется предупреждающая плашка с кнопками **«Перезагрузить»** и **«Перезаписать»**.

## 2. Журнал аудита изменений конфигурации (`object_config_audit`)

Все изменения свойств объектов, переменных, функций и событий фиксируются в таблице `object_config_audit`.

```http
GET /api/v1/objects/by-path/audit?path=root.platform.devices.pump-01&limit=50
```

В консоли администратора история правок узла доступна на вкладке **«История изменений»** в инспекторе объекта.

---

## 3. Индикация присутствия и временная блокировка ветки (`lease`)

### Мягкая индикация присутствия (`presence`)
Когда инженер открывает ветку дерева в режиме редактирования, веб-консоль отправляет по WebSocket сообщение присутствия:

```json
{ "type": "presence", "path": "root.platform.devices", "username": "ivan", "mode": "edit" }
```

Сервер рассылает коллегам список пользователей, работающих сейчас с этим узлом (время жизни отметки — 30 секунд). Сама по себе отметка присутствия запись не блокирует.

### Жёсткая аренда поддерева (`lease`)
Если инженер ведёт крупную перестройку ветки (например, целого цеха) и хочет временно запретить другим пользователям менять объекты внутри неё, он может оформить **аренду поддерева**:

```http
POST   /api/v1/objects/leases   { "pathPrefix": "root.platform.devices.shop-1", "ttlMinutes": 120 }
DELETE /api/v1/objects/leases?pathPrefix=root.platform.devices.shop-1
GET    /api/v1/objects/leases
```

Пока аренда активна, любые попытки других пользователей изменить узлы внутри `pathPrefix` отклоняются с кодом **`423 Locked`**.

## 4. Сравнение и слияние шаблонов (`blueprints`)

При доработке шаблонов и обновлении уже созданных экземпляров доступны методы предварительного просмотра конфликтов и пакетного обновления:

```http
POST /api/v1/blueprints/merge-preview
POST /api/v1/blueprints/merge-apply
POST /api/v1/blueprints/{id}/upgrade-instances?dryRun=true
```

---

## 5. Права владения ветками дерева (`ACL`)

В дополнение к базовым разрешениям (`READ`, `WRITE`, `INVOKE`) в списке доступа узла (`object_acl_entries`) поддерживаются укрупнённые уровни полномочий, наследуемые вниз по поддереву:

| Уровень доступа | Разрешённые действия |
|-----------------|----------------------|
| **`OWNER`** | Чтение, запись, вызов функций, управление правами доступа (`ACL`) и взятие ветки в аренду (`lease`) |
| **`EDITOR`** | Чтение, запись и вызов функций |
| **`VIEWER`** | Только чтение |

Назначение прав выполняется запросом `PUT /api/v1/objects/by-path/acl?path=<путь>` или на вкладке **«Доступ»** в инспекторе объекта.

---

## 6. Пакеты изменений (`Change Sets`)

Если нужно подготовить серию правок на нескольких узлах дерева, проверить отсутствие конфликтов версий и применить все изменения одной атомарной транзакцией, используются **пакеты изменений (`change-sets`)**:

```http
POST /api/v1/platform/change-sets
GET  /api/v1/platform/change-sets
POST /api/v1/platform/change-sets/{id}/preview
POST /api/v1/platform/change-sets/{id}/apply?force=false
```

Каждая операция в пакете может указывать ожидаемую ревизию узла (`expectedRevision`). Метод `/preview` заранее проверяет все целевые узлы на конфликты, а `/apply` применяет пакет целиком в одной транзакции.

> Для создания и переноса нового прикладного решения между стендами используйте полноценный манифест **`bundle.json`** ([Приложения](applications.md)), а `change-sets` применяйте для контролируемых точечных правок на уже работающем дереве объектов.
